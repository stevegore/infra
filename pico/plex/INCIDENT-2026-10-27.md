# 2026-10-27 — Plex on pico compromised, cryptominer

**Status:** contained and restored 2026-10-27. Plex account token rotation outstanding (see Follow-ups).
**Impact:** pico CPU pinned (about 7 of 12 cores) for at least 9 days by an xmrig-based miner inside the
`plex` container. The attacker had Plex owner-level API access and code execution as the in-container
`plex` user (uid 1000, which is `steve` on the host). No evidence of escape to the host or spread to
other containers.

All times are AEDT (Plex logs use `TZ=Australia/Sydney`).

## Summary

pico ran `plexinc/pms-docker:1.43.2.10687-563d026ea` (built May, deployed July) with 32400/tcp forwarded
from the internet. Automated scanners chained three Plex weaknesses:

1. **SSRF → owner token.** `GET /player/timeline/subscribe?protocol=http://127.0.0.1:32400/system/agents/...`
   on the companion proxy makes Plex call *itself* over loopback, which counts as trusted. That reaches the
   legacy `com.plexapp.agents.thetvdb` `GetResultFromNetwork` with a URL on the attacker's server
   (`127.0.0.1.<attacker-ip>.sslip.io`). Seconds later the same IPs make requests as
   `Token (stevegore)`, the server owner.
2. **Arbitrary file write.** As owner: `PUT /:/prefs?TranscoderH264Options=dump-yuv=<Codecs dir>/<...>/xd24185_251.so:qp=0`,
   then `GET /video/:/transcode/universal/start.m3u8`. x264's `dump-yuv` writes the attacker's bytes to that path.
3. **Code execution and persistence.** The transcoder loads `.so` files from the per-server `Codecs/`
   directory, so the planted "codec" runs as `plex`. It dropped the miner and watchdog, and it reran at each
   container start. It deleted itself after the 08:02 restart, which is why the Codecs directory's mtime
   matched the miner's relaunch.

Totals in the surviving logs (Oct 21–27): 662 `TranscoderH264Options` injections, 267 transcode starts,
374 `/system/agents/media/get`, and 145 `/:/plugins/.../resources/x` + `/system/:/resources/x` reads.
They came from 12 source IPs, so this was opportunistic mass exploitation, not a targeted attack.

## Why it stayed unpatched — Renovate never saw a Plex update

`renovate.json` automerges pico image bumps, but the dependency dashboard (issue #9) listed
`plexinc/pms-docker 1.43.2.10687-563d026ea → [Updates: 1.43.2.10687-563d026ea]`. Docker versioning reads
the trailing `-<githash>` as a *compatibility* suffix. Every Plex release has a different hash, so none was
ever considered an upgrade of the running tag. 1.43.4 (Sep 10) and 1.43.5 (Oct 20/26) went by unnoticed.
1.43.5.11079 lists `(Security) Increase security on requests arriving through a proxy (PM-6201)`,
`Fixed request locality when the server's local network interface is unknown (PM-6183)` and
`(DVR) Harden validation of the post-processing script setting (PM-5538)`. Matching these to the
chain above is an inference from the release notes. Plex has not published a mapping.

## Why it went unnoticed for 9+ days

Nothing alerts on host CPU or load. Uptime Kuma only checks reachability, and Plex stayed responsive with
5 of 12 cores free. It was only spotted by eye.

## Scope checks (clean)

- Host: no new crontab entries, systemd units, `authorized_keys` or shell rc changes; no host processes or
  sockets for the IOCs above.
- `/srv/movies`, `/srv/tv` (mounted read-write): no executables or scripts modified since Oct 10.
- `plex_plex-temp` volume: no executables or hidden files.
- Container not privileged, no Docker socket, no added capabilities.

## Remediation done

1. Stopped the container. Removed `/config/.daemon` and `/config/.f`. Wiped every codec bundle under
   `Codecs/` (Plex re-downloads them; the old set is in `codecs-backup.tgz` in the evidence dir).
2. Recreated the container from `1.43.5.11079-b3b13e506`. A *restart* keeps the writable layer, and the
   `/tmp` droppers sat in that layer through every restart since July. Only a recreate removes them.
3. `renovate.json` rule 10: `plexinc/pms-docker` uses
   `regex:^(?<major>\d+)\.(?<minor>\d+)\.(?<patch>\d+)\.(?<build>\d+)-[0-9a-f]{9}$`, so Plex bumps now
   automerge like every other pico image.

## Follow-ups

- [ ] **Rotate the Plex account token** (not doable from here): change the plex.tv password with "sign out
      of all devices", then review Authorized Devices and Friends/Sharing for anything unfamiliar. The
      attacker used the owner token for 6+ days, and it is the account token, not just a server token.
- [ ] Decide whether the 32400 router port forward is still needed. Every attack came in on it directly;
      none came through `plex.stevegore.au` (Caddy), which is already the advertised remote address.
- [ ] Add a pico load/CPU alert (e.g. Pushover when 15-min load > 6 for 30 min) using the existing
      `pushover-failure@` plumbing.
- [ ] Look for other images with hash-suffixed tags that Renovate can't compare: run a dashboard entry
      whose only listed update is its current value.
